## Domain model — what every future feature must stay consistent with

**Availability (`src/domain/availability.js`, `computeAvail()`)** — a recipe's *strict*, unadapted state: `perfect` / `good` / `almost` (exactly one missing required ingredient) / `unavail` (2+ missing required). Resolves each component through, in order: (1) exact ownership or a household basic, (2) a Can-provide form conversion (Concept 2 — owning Lemon satisfies a Lemon Juice component), (3) a recipe-scoped adopted alternative (`recipe_component_alternatives`, per-recipe, author-curated). No fuzzy/name matching anywhere — always explicit ids, ancestry, or substitution-group relationships (a standing `AGENTS.md` rule).

**Makeability (`src/domain/makeability.js`, `computeMakeability()`)** — wraps `computeAvail()` and adds two more tiers *only when strict already has a missing required component*: tier 4, an owned **general** catalogue substitute (`ingredient_substitutions` — suggestion-only elsewhere, but promotes to an actual resolution here once owned); tier 5, a satisfiable **homemade preparation** (`ingredient_preparations`/`ingredient_preparation_inputs` — one level deep only, an input can never itself be another substitute or another preparation; DB-enforced depth guard). All-or-nothing: if even one missing required component can't resolve via tier 4/5, the whole adaptation fails (no partial credit). Returns `{ strict, adapted, display }` — **`display.tier` (`perfect`/`good`/`almost`/`unavail`/`adapted`) is the one field every user-facing primary-status surface must read**, never the bare `strict.avail` — a recipe resolvable via an owned substitute or preparation must never show a contradictory "Unavailable" anywhere. `adapted.resolvedRequired` carries the *actual* per-component resolution chosen for this recipe with this user's bar (never every catalogue possibility) — this is the one structured source any UI needs for "what do I actually need to do" (see `buildAdaptedCardActions()`, reused by both `CocktailCard`/`SmallCard`).

**General substitutes vs. recipe-scoped alternatives — deliberately two separate mechanisms, never merge them:** a general substitute (`ingredient_substitutions`) is catalogue-wide and suggestion-only *unless owned* (then it's tier 4 above); a recipe-scoped alternative (`recipe_component_alternatives`) is authored per-recipe and always affects that recipe's own strict tier 3. Different tables, different code paths, on purpose.

**Household basics** (`ingredient_types.assumed_available`, admin-managed via an onboarding-config table) resolve by exact id only — never propagated to ancestors/descendants beyond the normal ownership walk.

**Linked Variations** (`recipe_relationships` table) — one base → many variations (`unique(recipe_id)` makes the whole graph a forest of trees, never a general graph); a cycle (including a self-link) is invalid data and rejected at write time by a `BEFORE INSERT/UPDATE` trigger; **member-facing display is always exactly one hop in either direction, never a recursive family tree**, resolved by the pure `src/domain/recipeRelationships.js`. The relationship is pure metadata + navigation — it never affects either recipe's own ingredients, instructions, or availability, and a makeable variation never makes its base read as makeable (or vice versa). `save_recipe()` (a single atomic RPC) is the one path that saves a recipe's fields, components, taste tags, AND its relationship together — always use it from `services/recipes.js`, never a sequence of separate calls, or a rejected relationship change can leave other fields half-saved.

**Admin/moderator rules:** members add products, never new ingredient types. A recipe's owner (or an admin, classic-catalog only) can edit it — `recipe_is_visible()`/`recipe_is_editable()` are the two RLS helpers this whole app composes for every recipe-adjacent authorization decision, including Linked Variations' own read/write policies.

## RLS & schema state

- Every exposed table ships RLS in the same migration as the feature that needs it; default-deny for anon and non-members.
- `supabase/tests/rls_suite.sql` covers every RLS-protected table introduced so far (extend it table-by-table alongside new work, don't start a second suite file). No local Postgres/Docker in this sandbox, so it runs directly against the hosted linked project via `npx supabase db query --linked --file supabase/tests/rls_suite.sql`, wrapped in one transaction rolled back at the end — never leaves fixture data behind. Simulates each identity by switching the `role` GUC + `request.jwt.claims`.
- Every `SECURITY DEFINER` function needs an explicit `revoke ... from public, anon, authenticated` then a narrow `grant` — Postgres grants `EXECUTE` to `PUBLIC` by default on `create function`, so skipping the revoke leaves it callable by anyone regardless of the narrower grant. Verify with `npx supabase db advisors --linked --type security` after any migration adding a function.
- 65 migration files on disk as of 2026-09-13. A migration-ledger mismatch that blocked `db push` earlier in the project **was diagnosed and resolved on 2026-09-07** via `supabase migration repair` (ledger-only — no schema/data touched); don't assume it's still broken, but do run `npx supabase migration list --linked` before a `db push` in a new session just to confirm `local == remote` throughout.
- PostgREST resource-embedding selects can't be validated via `supabase db query` (that bypasses PostgREST's embed resolution) — sanity-check the real query string with a direct `curl` against the REST endpoint instead (see `AGENTS.md`'s own testing section for the exact command shape).

## Testing & tooling constraints

- Pinned toolchain: `corepack pnpm@10.34.3` for install/test/build. **Never run bare `npx pnpm ...`** — with no `packageManager` field pinned, it fetches a newer pnpm that has previously wiped `node_modules` and failed on this machine; recover with `corepack pnpm@10.34.3 install --frozen-lockfile`.
- `pnpm test` (Vitest) covers `src/domain/` (and now `src/lib/`) only — **no jsdom/testing-library is installed**, so no component-rendering test is possible in this repo today. When a presentational feature needs real test coverage, the established pattern is to extract the actual *decision* (what text/order/condition to show) into a small pure function in `src/domain/`, tested directly, and leave the surrounding JSX as a directly-readable, one-line structural guarantee — not to add a rendering framework. `vitest.config.js` runs in a plain Node environment (confirmed: no global `localStorage` there) — a `src/lib/` module that touches `localStorage` (e.g. `recipeDrafts.js`) is still testable by installing a tiny in-memory `localStorage` stub onto `globalThis` inside the test file itself (see `recipeDrafts.test.js`) — no new dependency needed for that specific gap.
- `pnpm format` (oxfmt) has a real bug in this Windows sandbox (CRLF-related) — **do not run the repo-wide formatter.** When formatting genuinely matters, reflow only the touched files by hand or check them in isolation.
- **No browser automation is available to Claude in this sandbox.** Automated tests/build passing is not equivalent to UI verification. Per AGENTS.md's "Pre-commit verification" rule, a user-visible/runtime-affecting change should be manually exercised in the local dev app *before* commit — since that's not mechanically possible here, say so explicitly before committing and name exactly what remains unverified, rather than silently deferring all verification to after push. The user's own manual check (on a real device, after pushing) remains the actual verification step for anything Claude can't exercise itself.
- Manual verification requests should use ordinary navigation and existing data wherever possible — avoid asking for destructive setup (e.g. clearing My Bar) unless genuinely necessary to exercise the change.
- Commit workflow: stage the relevant files (never a blind `git add -A` across unrelated in-flight work), run tests + build, then follow AGENTS.md's "Pre-commit verification" rule (dev-app check where possible, otherwise an explicit unverified-flag) before committing with a heredoc-authored message (a literal bash/Git-Bash quirk on this Windows sandbox mangles backtick-quoted code identifiers inside a plain `-m` string), then push. Don't wait to be asked each time once this pattern is established for a session, unless told otherwise.
- **There is no separate dev/staging Supabase project — the local dev frontend and production frontend both read the one live catalog database** (clarified 2026-09-15 during the ingredient enrichment pass). For a *data-only* catalog change (no app/code touched), the verification standard is: (1) re-fetch live state immediately before writing, (2) detect any concurrent conflict rather than overwrite it, (3) apply transactionally, (4) full DB read-back/integrity verification (every field/relationship changed, no duplicates, no unintended reverse relationships, unrelated rows untouched). **Manual local-frontend verification is not a required separate step for a data-only change once (1)-(4) pass** - don't ask for it just to re-view a field the DB read-back already conclusively confirmed (aliases, icons, colors, priorities, parent relationships, substitution rows/notes, descriptions, other plain persisted metadata). It's still worth a manual check when the change has actual UI/runtime behavior DB state alone can't establish - e.g. confirming a brand-new field is genuinely wired into whatever component is supposed to read it, not just present in the table. This does NOT weaken the separate rule for actual app/code/UI changes, which still requires local dev-app manual verification before commit/push exactly as AGENTS.md's "Pre-commit verification" rule describes.

## Active plans

**The Ingredient Catalogue Enrichment Pass (Batches 1-13 + final catalogue-wide audit and cleanup) is formally COMPLETE as of 2026-09-16.** Batches 1-6, **Batch 7 (Liqueur, 7a-7f)**, **Batch 8 (Spirit, 8a-8g)**, **Batches 9 (Mixer), 10 (Beer), 11 (Dairy & Eggs), 12 (Sauce), and 13 (Other)** are all done and verified, followed by a final catalogue-wide integrity/consistency audit and approved cleanup pass (see below) that closed out every finding worth acting on. `docs/plans/` still contains only `archive/`.

  **The active piece of work is now the Existing Cocktail Adaptation Pass** (started 2026-09-16), which runs *before* the Adaptation/Replaceability Model Audit rather than after it - the model audit should be grounded in real evidence gathered from actually auditing every existing cocktail, not run as a purely theoretical redesign first. Full methodology, clarified/finalized 2026-09-16 after two rounds of correction mid-Batch-1 (see below) - **this is the authoritative version, superseding earlier same-day summaries**:

  **Purpose.** The existing shared/active cocktail catalogue (76 recipes) largely originated from external recipe source(s). That's a useful starting dataset, but Rusty Pipes should not merely reproduce another site's recipes or taxonomy uncritically. The purpose of this pass, per cocktail: *research it, establish a good canonical Rusty Pipes recipe, and research how a home bartender can reasonably adapt it.* Worked ~7 cocktails at a time specifically so real editorial/product decisions get reviewed before they're applied - **this is deliberately not a 76-recipe bulk cleanup**.

  **Two layers that must stay distinct, always:**
  - **Canonical recipe truth** - "what is this cocktail actually supposed to contain?" Independently audit, for every cocktail: ingredients, ingredient specificity, quantities, units, required-vs-optional roles, component roles, preparation/technique, glassware, garnish, Family/classification, description (where factually relevant), and any other persisted metadata relevant to representing the drink correctly. Never assume an existing value is intentional/correct merely because other recipes share the same convention (import-artifact risk - see below). Never assume one published formulation is uniquely correct when multiple legitimate formulations genuinely exist - choose a well-supported, practical canonical representation and explicitly explain material judgment calls.
  - **Adaptation / home-bar usefulness** - "what can I reasonably use instead, and how will it differ?" Researched separately, never by making the canonical recipe artificially generic to improve makeability (if a cocktail genuinely calls for Aperol, Aperol stays canonical; Campari-as-substitute is an adaptation-layer finding, not a canonical rewrite). Classify each adaptation finding as: an existing catalogue substitution that already correctly works, a new broadly-useful global substitution, a recipe-specific alternative, a recognized-variation/different-cocktail relationship (not encoded as a substitution), or something not worth recommending. Evaluate substitutions in the actual recipe's context - quantity, proportion of the total drink, role, required/optional status, interaction with other ingredients, sweetness/acidity/bitterness/ABV/aroma/texture/color/dilution, preparation method, and whether the result stays coherent and worthwhile or actually becomes a different recognized cocktail. The same substitution can behave very differently across two different recipes - never evaluate ingredient-pair-in-isolation.

  **Ingredient specificity rule**: use exactly the specificity the cocktail itself justifies. Generic/style-level when the drink genuinely calls for that generic ingredient and a source merely happened to name a brand. A specific brand/product/regional style stays when it's genuinely defining to that cocktail's identity (Aperol in an Aperol Spritz; Cognac in a Sidecar/Alexander/Sazerac/Vieux Carré/Stinger/Between the Sheets, already independently confirmed via Batch 8d's research). Never inherit unnecessary specificity merely because a source site happened to use one bottle; never strip legitimate specificity merely to raise the makeability pass rate.

  **Never infer a `family` value or an ingredient's specificity is intentional merely because it matches other recipes already in the catalogue.** Much of the catalogue was imported from external source(s), so shared conventions may be inherited import artifacts, not deliberate choices - research each cocktail's correct family and each ingredient's correct specificity independently from real cocktail knowledge every time, never from catalogue-internal consistency.

  **When research discovers something wrong or unexpected mid-batch - a decision point, never a thing to silently ignore or silently fix.** Do not knowingly leave a confirmed problem behind merely because it wasn't anticipated when the batch started, and do not automatically defer it to a future pass either. Also do not overreact into a large redesign. Instead: (1) research the issue sufficiently, (2) explain what's wrong and why, (3) determine the correct or plausible Rusty Pipes options, (4) present the decision to Max as part of the *current* batch, (5) if the correct representation needs a small model/schema/catalogue change, name that concrete requirement explicitly, (6) stop for a decision when necessary. This is one of the main reasons batches stay small (~7) rather than bulk-processing - concrete example: when Alexander was found not to genuinely be a `Flip`, the right move was to research what it actually is, state whether Rusty Pipes' Family enum can represent that, and if not, name the smallest sensible enum change - not "there's no better value, so leave the wrong one."

  **Batch workflow** (11 steps, repeated per batch): (1) fetch fresh live recipe/catalogue data - never trust a prior session's snapshot, (2) research each cocktail, (3) audit canonical recipe correctness, (4) audit realistic adaptations, (5) identify confirmed corrections, (6) surface unexpected findings/decisions rather than ignoring them, (7) present a concise proposal to Max, (8) after approval, re-fetch affected live state, check for conflicts, apply transactionally, comprehensively verify by DB read-back, (9) no redundant manual DEV verification required for ordinary persisted data already conclusively verified via DB, (10) record durable findings/methodology, (11) proceed to the next batch.

  **Relationship to the later Adaptation/Replaceability Model Audit**: accumulate concrete findings throughout every batch - exact-ID substitution limitations, parent-ancestry behavior, role/quantity effects, generic vs. recipe-aware substitution notes, recipe-specific alternatives, preparation-based availability, ranking/discovery, recognized-cocktail-transformation boundaries, and anything else the current makeability model represents poorly. Do **not** redesign `computeMakeability()` merely because one interesting case appears mid-batch - gather evidence first; the model audit happens only after the whole existing catalogue has been reviewed, using the accumulated evidence, not as a theoretical exercise.

  **Ordering/resume point**: `visibility='shared' AND moderation_status='active' ORDER BY lower(name)` - 76 recipes total at pass start. Batch 1 = recipes 1-7 (Alexander, Americano, Angel Face, Aviation, Bee's Knees, Bellini, Between the Sheets). Batch 2 = recipes 8-14 (Black Russian, Bloody Mary, Bloody Mary (Practical Version), Boulevardier, Bramble, Brandy Crusta, Caipirinha).   - **Catalogue truth is strict; adaptation is permissive but curated.** Two different questions: "what is this ingredient, accurately?" (taxonomy/category/parent/alias/description - stays rigorous) vs. "what can I reasonably make with this, and how will it differ?" (substitutions - deliberately more permissive). The adaptation threshold is *"would this usually produce a worthwhile/drinkable home-bar variation, and can Rusty Pipes clearly explain the important difference?"* - it does NOT require equivalence, canonical precedent, historical precedent, or a named cocktail variation; those are supporting evidence, never a requirement.
  - Core user-facing concept: **"You can make this; here's how it'll be different."** Never silently rewrite the canonical recipe; adaptations stay identifiable and explained.
  - **No Experiment/Try-It tier.** Adaptations Rusty Pipes surfaces must remain curated recommendations with reasonable confidence the result is worthwhile - permissive is not the same as speculative.
  - **Global substitutions never assert equivalence** - a substitution can acknowledge a substantial, honestly-described change and still be worth proposing.
  - **When suitability strongly depends on the complete cocktail's structure, prefer a future recipe-specific alternative (`recipe_component_alternatives`) over an unreliable global substitution.** (Origin: Batch 9's Soda Water dilution/carbonation-role principle, reapplied in Batch 10 for Lager/Ale and Stout/Pale Ale, and in Batch 11's reasoning for why Cream/Milk *did* clear the global bar.)
  - **Quantity/ingredient role may affect substitution suitability** (a 0.3ml accent vs. a 45-60ml base pour vs. a dash/drop seasoning are different propositions) - not yet implemented, an open question for the Adaptation/Replaceability audit. Reinforced with real data in Batch 12: every current Sauce recipe reference is `optional`-role, dash/seasoning-scale, and can never gate strict availability at all. **Batch 13 sharpened this further: role and quantity are independent dimensions, not correlated** - Other-category evidence shows dash-scale `required` components (Orange Flower Water, Vanilla Extract in Ramos Fizz) and structural-volume `required` components (the two purées) side by side, plus the same ingredient (Black Pepper) is `optional` in one recipe and `required` in another - role must be read per-recipe-component, never assumed from the ingredient type or from quantity.
  - **Parent ancestry is a taxonomy/makeability relationship, not a general-compatibility one.** Owning a child satisfies its generic parent - only create that relationship when it's actually desirable (repeatedly gotten wrong and fixed: Peach-Flavored Whiskey, Spiced Rum, Peach Vodka all had to be detached after creating misleading makeability).
  - **Foundational ingredients are not gated by current recipe references.** Zero recipe references is evidence to weigh, never sufficient reason alone to reject an otherwise-major, practically-stocked ingredient (established via IPA in Batch 10, reinforced by Aquafaba/Egg-family reasoning in Batch 11).
  - **Ingredient preparation vs. recipe formulation are separate concepts** (Batch 11): how a standard ingredient is normally made, vs. the specific ratio one particular cocktail calls for.
  - **Initial Israeli market relevance is a legitimate priority signal** alongside international classic-cocktail relevance, not subordinate to it (established via Arak in 8f) - but don't add something merely because it's regionally available with no real usefulness.
  - **`Can be replaced by` (substitution) vs. `Can provide` (component extraction) vs. parent/child (taxonomy) are three distinct mechanisms** - don't reach for the wrong one merely because it's more convenient (Batch 11's Egg → Egg White/Yolk had to be Can Provide, not parent/child, since white/yolk aren't "kinds of" egg).
  - **Personal Substitutions / My Preferences, Clone/Adapt Recipe, the Classic/Flexible makeability mode, and the Living Catalogue (user-added ingredients) are all recorded future work, not part of the current enrichment pass** - see their own dedicated paragraphs above. Do not begin designing or implementing any of them during catalogue enrichment.

  **Future product architecture idea (not scoped, not started, must not expand current work) - Cocktail Map / Discovery Graph.** Recorded 2026-09-16 as a concept to preserve, nothing more: cocktails as nodes, with meaningful transformations/relationships between them as edges - potentially integrating Linked Variations, ingredient substitutions/adaptations, cocktail families, and My Bar's "unlocked" state (which cocktails become reachable as the user's bar grows). This is a future product-architecture direction only; it must not influence or expand the scope of the current ingredient enrichment pass or the upcoming Adaptation/Replaceability audit.

  **Core product framing (2026-09-15, 8e):** Rusty Pipes should teach both (1) how the canonical/classic cocktail is made, and (2) what enjoyable version the user can make with the bottles they actually own. ADAPTATION ("what can I reasonably make with this, and how will it differ?") is deliberately a *lower, different* bar - a global practical substitution does NOT require equivalence, canonical precedent, a named classic variation, or preservation of the original cocktail's identity. Those are useful supporting evidence when they exist, never a requirement.
